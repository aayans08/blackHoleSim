# Legacy Python + GLSL reconnaissance: blackHoleSim

## 0. Bottom line
- **No legacy file integrates a real light path.** The repo contains 7 different ways of bending light, and all of them are ad-hoc nudges whose size depends on step size. In one of them (InterstellarRenderer.py and shaders.py) the bend points away from the hole on the outgoing half of the path, so the net deflection roughly cancels out (details in §3).
- **There is no real astronomy data anywhere.** No orbital elements, ephemerides or star catalog exist (grep for `semi|eccentric|AU|kepler|ephemer|hipparcos|catalog|magnitude` over `*.py` finds nothing relevant). The only real numbers are:
  - G, c and M☉ (blackHoleEngine.py:6-8)
  - the Rs, photon-sphere and ISCO formulas (blackHoleEngine.py:16-26)
  - Earth and Moon radii (PandaUniverse.py:433, 446)
- **Body positions are arbitrary**, e.g. Earth at (100,0,0), PandaUniverse.py:434.
- **The Barnes–Hut code is never run by any renderer.** `NBodySimulation` and `BarnesHutNode` are only referenced inside blackHoleEngine.py, and `PandaUniverse.setup_physics()` is just `pass` (PandaUniverse.py:577-581). The code also has a Velocity-Verlet bug (§2.2).
- **Carry forward ideas, recipes and parameters, not code.** The ranked list is in §5.
- **The Rust code depends on no Python file**, so archiving is safe (§6), with two caveats:
  - `shaders/` mixes Rust WGSL with legacy GLSL.
  - All legacy files are untracked in git (`git ls-files` returns only `.gitattributes`). A tarball or commit is needed before anything is deleted.

## 2. Per-file analysis

### 2.1 PandaUniverse.py (the file the owner has open)

**What it does:** a Panda3D scene graph containing:
- an inverted-sphere starfield skybox (236-253)
- a black sphere for the event horizon (313-320)
- a point-sprite accretion disk (346-422)
- textured Earth, Moon and Sun spheres (424-532)
- a spherical-coordinate orbit camera and a HUD (620-642)

**Real or fake, item by item:**
- **Scale is not real.** The comment says "1 render unit = 10 km" (109-110), and the 10 M☉ hole gets the correct Rs of 29.5 km → 2.95 units. But Earth `radius=6.371` × 0.1 = 0.64 units, i.e. 6.4 km, which is 1000× too small. Earth sits 100 km from the hole (`position=(100,0,0)`, 434) and the Sun is 20 "km" in radius (457). No size or distance in the scene is physical.
- **The "photon sphere / Einstein ring" (322-335) is fake.** It is three full translucent orange spheres at 1.5 Rs. Their near faces are drawn over the opaque horizon (`setBin('fixed')`, alpha 0.4), so the "black hole" appears as an orange-tinted ball. There is no lensing.
- **The "volumetric accretion disk" (346-422) is fake.** It is 5 layers × 50 rings × 200-400 points (≈74,500 points) drawn as fixed 4-px screen points (`setRenderModeThickness(4)`, 413). Colour is a 3-band step function of normalised radius (391-396). The whole disk rotates rigidly at 10°/s via `setH` (650), not with Keplerian differential rotation.
- **The lensing shader (534-575) is dead code.** `lens_shader` is a local that is never applied. Even if it were, it outputs the distorted UV as a colour (567). Line 573 sets a shader input on a node that has no custom shader.
- **The physics hook is empty.** `setup_physics` is `pass` (577-581). The engine is used only for the radius formulas.
- **Lighting is inconsistent.** There is a DirectionalLight "sun" fixed at HPR (45,-60,0) with a shadow caster (226-231), plus a separate PointLight on the Sun sphere (525-529). Ambient is 0.05 (221). `setShaderAuto` is used (234), so none of `shaders/*.frag` is ever used.
- **The Earth night and cloud textures are loaded but never applied.** `create_planet` accepts `texture_night` and `texture_clouds`, but only `texture_day` is ever used (481-482).
- **The atmosphere is a 1.03× translucent blue shell with lighting off (493-499).** There is no scattering and no limb brightening.
- **Texture paths mostly miss.** The file expects `planets/*_4k.jpg` (182-194). On disk, the Moon and Mars maps exist only as `textures/moon.jpg` and `textures/mars.jpg`, so the Moon renders as a grey fallback. The normal, specular, Jupiter and Saturn maps do not exist at all.
- **The controls do not match what is printed.** WASD is printed (77) but never bound; only arrows, Q/E, R and Esc are (583-599). `move_speed` (118) is unused. Each key press moves a fixed step (`accept` fires once per press), not continuously.
- **Every body spins at 5°/s**, the Sun included (653-654).

**Worth porting:**
- the *idea* of separate cloud and night layers per planet (the API at 467-469)
- the orbit-camera-around-a-target mode (123-130, 601-618) as one camera mode
- the texture quality flags (trilinear filtering + 16× anisotropic, 98-100 and 203-205)

Nothing else in this file should be carried over.

### 2.2 blackHoleEngine.py (Barnes–Hut)

**Physics that is correct:**
- G = 6.67430e-11 (CODATA 2018), c exact, M☉ = 1.989e30 (6-8)
- Rs = 2GM/c² (16-18), photon sphere = 1.5 Rs (20-22), ISCO = 3 Rs = 6GM/c² (24-26). All three are correct for Schwarzschild.

**Barnes–Hut implementation (40-158):**
- 2D quadtree or 3D octree, chosen by `dimension`
- monopole only (total mass + centre of mass)
- opening criterion `size/distance < θ` with θ = 0.5 (146)
- Newtonian force `G m₁ m₂ / r²` (148-151)
- the root box is 1.5× the bounding span (186-193)

It is real Newtonian gravity with the standard algorithm (Barnes & Hut 1986, https://doi.org/10.1038/324446a0). There are no post-Newtonian or GR terms.

**Bugs and limits:**
1. **Velocity-Verlet bug.** `old_acceleration` is one scalar variable that is overwritten inside the first loop (221). The second loop (230) therefore applies the *last body's* old acceleration to every body. The fix is to use each body's stored `body['acceleration']`.
2. Forces are computed twice per step: two tree builds (206, 224) and two force passes. A standard kick-drift-kick (KDK) leapfrog reuses the previous step's force.
3. **No softening.** `distance < 1e-10` returns zero (142), so close encounters blow up.
4. **Coincident bodies cause infinite recursion.** `insert` keeps subdividing (68-72). A single body gives a root of size 0 (193).
5. **Bodies can be silently dropped.** `_insert_to_child` does nothing if no child contains the point (113-118), e.g. because of float rounding at the boundary. The parent's mass and centre of mass already include that body, so the tree becomes inconsistent.
6. **Massless test particles break it.** It computes force and then divides by mass (213, 227), so a body with m = 0 (a probe or spacecraft) divides by zero. The API should return acceleration instead.
7. Recursive Python with dict bodies, so it is O(N log N) in theory but very slow in practice.
8. `BlackHoleEngine.add_body` (28-37) stores bodies but never integrates them.

**Worth porting:** the algorithm and its θ parameter, rewritten in Rust as:
- a flat, cache-friendly octree in f64
- Plummer softening
- optional quadrupole moments
- KDK leapfrog with per-body (block) timesteps
- rayon parallelism, or a GPU tree for 10⁵+ bodies

This suits star clusters like the one in the reference screenshot, and galaxies. For Solar-System accuracy, Barnes–Hut is the wrong tool: use direct N² summation with a high-order or symplectic integrator. REBOUND's IAS15 (https://arxiv.org/abs/1409.4779) and WHFast (https://arxiv.org/abs/1506.01084), with code at https://github.com/hannorein/rebound, are good algorithmic references; reimplement rather than copy.

### 2.3 InterstellarRenderer.py
**What it does:** a full-screen fragment-shader ray march with 500 steps (60). The camera is fixed at `(0,0.5,-35)*zoom` and rotated by Euler angles (1056-1065). The hole is Rs = 0.295 units (1098).

**Lensing (221-243):** the bend direction is `cross(toCenter, cross(toCenter, dir))`, which equals `toCenter(toCenter·dir) − dir` = −(the part of `dir` perpendicular to the radius).
- On the **incoming** leg this bends the ray toward the mass.
- On the **outgoing** leg it bends the ray away from the mass.
- So a symmetric fly-by gets roughly zero net deflection.
- The strength is `Rs/r² × 0.2` per step (doubled inside 3 Rs, 235-238) regardless of step length. Only applied inside 20 Rs.

**Other notes:**
- **Accretion disk:** commented out (245-286).
- **"Photon sphere glow":** brightens rays by their closest approach (294-298). It is cosmetic.
- **Planet (316-445):** not a 3D object but a disc painted on the sky at a fixed direction (`dotPlanet > 0.85`). Its "normal" `normalize(rayDir − toPlanet·dot)` is not a sphere normal. **The material recipe is the most reusable creative content in the repo:**
  - multi-octave continents + coastline detail + `smoothstep` shoreline (334-341)
  - mountains only on land (344-348)
  - lakes (351-352), vegetation (355-357)
  - desert driven by latitude (360-361), polar ice (364)
  - two cloud octaves drifting over time (367-369), storm cells (372-373)
  - a palette of 9 surface colours (376-384)
  - `smoothstep` terminator (416-419)
  - night-side city lights limited to land and not under cloud (422-426)
  - ocean specular glint where there is no land or cloud (434-439)
- **Stars (469-616):**
  - three layers on a (θ, φ) grid: stars pinch at the poles and there is a seam at the atan2 wrap
  - five layers on plane projections (`dir.xy` at 518/534/560, `dir.xz` at 580, `dir.yz` at 595): every star in those layers appears twice, mirrored across the projection plane, because (x,y,z) and (x,y,−z) hash to the same cell
  - the hash is `fract(sin(x)*43758)` with arguments up to ~1000, which bands and repeats in f32 on GPUs (see https://www.shadertoy.com/view/4djSRW)
- **Nebulae (618-757):** five hand-placed blobs built from `sin`/`cos` products. Plausible palette (Hα red, OIII teal, reflection blue) but no structure.
- **Galaxies (759-1021):** recipes for 4 morphologies:
  - spiral: arms of the form `angle − log(r)·k` plus a core and bulge, 863-887
  - elliptical: `exp` profile, 811-814
  - edge-on: thin disk with a dust lane, 818-821 and 890-911
  - irregular: clumps, 825-847

  All use `dir.xy`, so they are mirrored front and back.
- **Milky Way:** a band at `abs(dir.y) < 0.25` (1023-1043). It assumes the galactic plane is the world XZ plane.
- **Post-processing (1071-1085):** Reinhard tone mapping, then gamma 0.85 (not 1/2.2), vignette, and a fake bloom applied *after* tone mapping.

### 2.4 RealisticRenderer.py
- Subclasses InterstellarRenderer to add an HDR pipeline:
  - rgba16f framebuffer (69-74)
  - half-resolution separable 5-tap Gaussian with a bright-pass (77-135)
  - ACES fitted curve + exposure + gamma (138-175)
- **The pipeline never actually runs.** `self.vao` is bound to the *scene* program (InterstellarRenderer.py:1114). `apply_bloom` and `tonemap_and_display` call `self.vao.render` (257, 264, 276), so the bloom and tonemap programs are compiled but never drawn. The scene is rendered 3 times instead.
- Even if wired correctly, the scene shader already tone-maps (InterstellarRenderer.py:1072), so the "HDR" buffer would hold LDR values.
- **Worth porting:** the pipeline design (scene in HDR → bright-pass → separable blur at half resolution → combine → exposure → ACES → gamma), with tone mapping only at the end. ACES fit reference: https://knarkowicz.wordpress.com/2016/01/06/aces-filmic-tone-mapping-curve/

### 2.5 RealisticBlackHoleRenderer.py
- **Claims "PROPER Schwarzschild geodesic integration" (5-6, 177). It is not.**
  - The "geodesic" is a radial pull `(Rs/r)/r² × (1+1.5Rs/r) × 0.1` per step (204-208).
  - `b_squared` is computed and never used (201).
  - It runs at most 150 steps (116) and escapes at 100 Rs.
- **The disk is never lensed.** It comes from a straight-line plane intersection from the camera (`renderAccretionDisk(camera_pos, ray_dir)`, 300) and is *added* on top of the shadow (301). That means no Einstein-ring images of the disk and no occlusion by the hole.
- `-origin.z / direction.z` divides by zero for rays parallel to the disk plane (232).
- There is no look-at. Camera position (378-382) and ray direction (290-294) come from the same angles through different rotation conventions, so the hole is not guaranteed to be centred.
- The HDRI path `textures/hdri/rogland_night_4k.exr` (74) does not exist (`textures/hdri/` is empty), and EXR loading is not implemented anyway (78-92).
- **Good idea:** working in units of Rs (35, 318-325). Keep shader math in Rs/M-normalised units.

### 2.6 GPUBlackHoleRenderer.py
- **Bend direction is right, size is wrong.** It uses `cross(cross(dir,toCenter),dir)` = the component of `toCenter` perpendicular to `dir`, which is the correct direction (203). The strength is `Rs/r² × 0.15` per step, independent of step length (197-204).
- **`bendLight` (88-102) is dead code** and never called. It is also wrong:
  - it uses "Einstein deflection" `4Rs/b`, but the weak-field angle is 4GM/(c²b) = 2Rs/b
  - it sets b = r
- **Good idea (207-224):** after a disk hit, *keep marching* and accumulate up to 3 crossings, with weight `exp(−accumulated)`. That is how the secondary and tertiary disk images form. Keep this structure.
- **Fake parts:**
  - the Doppler view direction is a hard-coded camera position `(0,3,-30)` (143), so it ignores rotation and zoom
  - the colour is a 5-band step function (147-163)
  - redshift uses `pow(metric, 0.3)` (170), an arbitrary exponent
- The post-processing applies gamma before Reinhard (266-268).

### 2.7 PygameRenderer.py
- A 2D pygame wireframe with a hand-rolled projection (39-63).
- **"Spacetime grid" (65-178):** a rubber-sheet funnel `−6Rs·exp(−d/2)/(1+0.3d)`. It is not an embedding of the metric.
- **"Einstein rings" (180-215):** circles at 1.5, 2.6 and 3.5 Rs. 2.6 Rs happens to be the correct shadow radius: the critical impact parameter is b_c = (3√3/2) Rs ≈ 2.598 Rs.
- **"Lensed disk halo" (284-348):** the far side of the disk is hand-placed above and below. It shows the right visual *target*, with no physics behind it.
- **Bug:** the HUD prints `engine.mass` (kg) labelled "Solar Masses" (439).
- `self.rays` is always empty (32). The `ray.py` it was written for exists only as a stale `.pyc`.
- **Worth porting:** only the *idea* of an educational overlay, redone with Flamm's paraboloid z = 2√(Rs(r−Rs)) (https://en.wikipedia.org/wiki/Schwarzschild_metric#Flamm's_paraboloid).

### 2.8 main.py
- A CLI dispatcher: `-u` RealisticBH, `-p` Panda, `-r` Realistic, `-i` Interstellar, `-g` GPU, default Pygame (10-150).
- It builds a **2D** engine for everything except Panda (17-20).
- Its fallback chains import other renderers (89-91, 108-110, 127-128).
- It contains no physics.

### 2.9 shaders.py (orphan)
- A string library:
  - main scene shader with MRT bright-pass output (23-416)
  - 9-tap separable Gaussian with weights 0.227/0.195/0.122/0.054/0.016 (419-467)
  - ACES + Reinhard tonemap + vignette (470-519)
- Same wrong-signed bend as InterstellarRenderer (342).
- The sky-decal planet gets Cook-Torrance GGX + Smith-Schlick + Fresnel-Schlick (81-117, 204-231), with texture, normal and specular sampler slots (31-34, 173-184).
- **Physics error:** the Rayleigh coefficient is `vec3(0.58, 0.42, 0.35)` (122). That makes red scatter most, the opposite of reality (Rayleigh ∝ λ⁻⁴, so blue is strongest). Do not port it.
- The Mie Henyey-Greenstein phase with g = 0.76 is correct (134-146).

### 2.10 texture_manager.py (orphan)
- A PIL → moderngl loader with a cache, vertical flip, mipmaps and anisotropy (26-86). That is a fine pattern, but the `image` crate replaces it.
- The procedural "Earth" (158-200) loops over 1M pixels in Python with `sin`-hash noise, giving binary land/ocean noise rather than continents.
- It monkey-patches `math.fract` (230-238).
- Nothing worth porting.

### 2.11 download_textures.py and the `textures/` folder
- **Source:** Solar System Scope URLs (78-161). Files are saved as `*_4k.jpg` but are the `2k_*` maps (2048×1024, confirmed with `sips`).
- **Licence:** CC BY 4.0, "use, adapt, and share … even commercially" (https://www.solarsystemscope.com/textures/).
- **Status:** these are another product's processed assets. The owner said "never copy another product's assets". Treat them as placeholders only, or replace them with NASA public-domain originals (Blue Marble https://visibleearth.nasa.gov/collection/1484/blue-marble, LRO/LROC, Viking MDIM).
- **What is actually on disk:** 6 unique images (Earth day, night and clouds; Moon; Mars; Sun; Milky Way), 7.0 MB total. Five pairs are byte-identical duplicates (`textures/*.jpg` vs `textures/{planets,stars,space}/*_4k.jpg`, same md5).
- **Not downloaded:** Earth normal and specular maps, Jupiter, Saturn, Saturn ring alpha (148).
- `create_simple_fallbacks` (167-202) writes random ellipses and random dots, which is garbage.

### 2.12 black_hole_shader.glsl (orphan)
- A Panda3D-style single file using `#ifdef VERTEX_SHADER`.
- Radial pull `Rs/r²`, fixed step 0.1, 100 steps (27-53). That is only 10 units of travel, so rays rarely reach the 100 Rs escape test and fall back to a flat colour (65).
- The disk is a straight-line plane hit added on top (124-126).
- Its "Doppler" is `1 + 0.3·sin(angle)`, which is pure decoration (104).

### 2.13 shaders/*.vert and shaders/*.frag (orphans, Panda3D `p3d_*` names)
- **atmosphere.frag:**
  - declares physically sensible parameters: Rayleigh β = (5.8, 13.5, 33.1)e-6 m⁻¹, H_R = 8 km, Mie β = 2e-5, H_M = 1.2 km, the Rayleigh phase 3/(16π)(1+cos²θ), and Henyey-Greenstein Mie (19-36)
  - **none of these are used.** The output is a `pow(1−N·V, 3)` rim term plus N·L (43-53)
  - the β_R, H_R and H_M values match Bruneton & Neyret 2008 / Nishita-style models
  - the header credits O'Neil, GPU Gems 2 (https://developer.nvidia.com/gpugems/gpugems2/part-ii-shading-lighting-and-shadows/chapter-16-accurate-atmospheric-scattering)
- **lensing.frag:**
  - "horizon" at 1.5 Rs (29), which is the photon sphere, not the horizon
  - 30 steps × 0.1 = 3 units of travel, with an escape test at 1000 that can never fire (16-45)
- **pbr.frag:** a standard GGX/Smith/Schlick shader. The normal, metallic and roughness maps are declared but unused (5-8, 57-59). It tone-maps inside the material shader (94).

### 2.14 requirements.txt, run.sh, RUN_PANDA3D.sh
- **requirements.txt:** pygame, numpy, panda3d, moderngl, Pillow.
- **run.sh is stale.**
  - It installs `scipy` and `numba`, which nothing imports (16).
  - It falls back to `main.py --improved --quality medium` (29). main.py has no such flags, so it silently runs the default Pygame renderer.
  - `--improved` matches `__pycache__/ImprovedCPURenderer.cpython-313.pyc`. The `__pycache__` folder holds `.pyc` files for 11 modules whose source has been deleted (UniverseRenderer, PhysicsBlackHoleRenderer, ray, etc.).

| Location | Bend direction | Strength per step | Step-size consistent? | Verdict |

**What to use instead:** the Schwarzschild null geodesic is reproduced exactly by a fictitious force in Cartesian coordinates, F = −(3/2) h² r̂ / r⁵, where h = |r × v| is conserved. Integrate it with RK4, or adaptive RKF45 near the photon sphere (Starless, https://rantonels.github.io/starless/: leapfrog first, later RK4).

**Disk appearance needs real terms too:**
- **Orbital speed:** all legacy disks use v = √(Rs/r) (InterstellarRenderer.py:139, RealisticBlackHoleRenderer.py:261, GPUBlackHoleRenderer.py:142), which is √2 too high even in the Newtonian limit. The correct Newtonian value is v/c = √(Rs/2r). The speed a static observer measures in Schwarzschild is √(Rs / 2(r−Rs)), which is 0.5c at the ISCO.
- **Doppler and redshift:** combine the relativistic Doppler factor 1/(γ(1−β·n̂)) with the gravitational factor, and scale observed intensity by g⁴ (bolometric). The legacy exponents `pow(metric, 0.3)` and `0.4` are arbitrary. For the full treatment see DNGR, https://arxiv.org/abs/1502.03808.
- **Temperature:** use T ∝ r^(−3/4)(1−√(r_in/r))^(1/4) (Shakura–Sunyaev 1973, https://ui.adsabs.harvard.edu/abs/1973A%26A....24..337S), then Planck → CIE XYZ → sRGB. This replaces the legacy 3-7-band colour step functions.

**Rust note (outside this audit's scope):** `shaders/compute.wgsl:76-83` still uses an ad-hoc deflection `(1.5·rs)/r² · (to_bh + v_perp/r)`, and the disk Doppler is clamped to [0.5, 2] (compute.wgsl:249).

## 4. How the legacy code compares with the reference screenshot
The reference shows:
- a hazy, dusty, Mars-like planet with a soft orange limb glow and an extended twilight terminator
- terrain detail: a canyon/rift, craters, bright basins, a cyclone, wispy clouds
- a blue-white star cluster
- a dense, fine star field
- faint dust lanes in the Milky Way

**Nothing in the legacy code reaches this.** The closest pieces:
- **Planet material:** the layered recipe in InterstellarRenderer.py:333-439 (clouds, storms, terminator), with real noise and real sphere geometry.
- **Rim glow:** the unused coefficients in atmosphere.frag:19-36, fed into a real scattering model, e.g. Hillaire 2020 LUTs (https://sebh.github.io/publications/egsr2020.pdf) or Bruneton (https://ebruneton.github.io/precomputed_atmospheric_scattering/).
- **Star cluster:** Barnes–Hut (for the dynamics) plus a real star-rendering path. The legacy star fields are not usable.

## 5. Ranked list of what to carry forward

1. **Constants and BH radii** (blackHoleEngine.py:6-26). Re-express them via GM (IAU 2015 nominal GM☉ = 1.3271244e20 m³ s⁻², https://www.iau.org/static/resolutions/IAU2015_English.pdf) in f64. ## 6. Archive safety

**The Rust code does not depend on any Python file.**
- **Source includes:** src/main.rs includes only `include_str!("../shaders/compute.wgsl")` (295) and `include_str!("../shaders/display.wgsl")` (300). There is no `std::fs`, `Path`, `File::open`, `std::process`, `Command` or `.py` reference, and no `textures/` or `assets/` path.
- **Environment map:** generated procedurally in Rust (`create_starfield`, main.rs:277-278, 523-560). `textures/` is never read. The `image = "0.24"` dependency in Cargo.toml is not `use`d anywhere in main.rs.
- **Build:** there is no `build.rs`. Cargo.toml dependencies are wgpu, winit, pollster, glam, image, bytemuck, futures, instant and env_logger, with no pyo3. A grep of Cargo.lock for "py" matches only `zerocopy`.

**Caveats:**
1. **`shaders/` is mixed.** Keep `shaders/compute.wgsl` and `shaders/display.wgsl` where they are. Archive only `atmosphere.*`, `lensing.*` and `pbr.*`.
2. **Nothing legacy is in git.** `git ls-files` returns only `.gitattributes` (one commit, `43c083b`). Create the tarball, or commit, *before* deleting anything, or the code is lost.
3. **The Python files import each other.** main.py imports the renderers, RealisticRenderer subclasses InterstellarRenderer, and PandaUniverse imports blackHoleEngine. Archive them as one set.
4. **Docs still describe the Python layout** (CLAUDE.md "Legacy Python (kept for physics reference)"; the other `*.md` guides were not audited) and need updating after the archive.
5. **Disk space** (relevant to the ~3.4 GB limit):
   - all legacy Python + GLSL source is about 190 KB uncompressed
   - `__pycache__/` is 424 KB and can be deleted
   - `textures/` is 7.0 MB, of which ~3.5 MB is duplicates
   - `target/` is 385 MB and can be rebuilt with `cargo clean`
