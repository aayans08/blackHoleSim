### 3d. Defects in the Rust code (not stated in any doc)

I did not run the binary; these come from reading the code and doing the arithmetic.

1. **The ray is too short to reach anything.** Each ray covers at most 150 × 0.1 = 15 km (compute.wgsl:216-217). The camera starts about 301 km from the hole (main.rs:58-61). So no ray from the start position reaches the horizon (29.8 km) or the escape radius (2000 km); every pixel falls through to the environment sample at :281. Bending over 15 km is roughly 0.4°, so lensing is effectively invisible unless the user flies to within ~15 km of the horizon.
2. **The camera starts looking away from the hole.** Forward is (0, −0.199, −0.98) (main.rs:62-63, 68-75); the hole lies about 88° off-axis in the −x direction. With a 75° vertical FOV and 1.6 aspect, the horizontal half-FOV is about 51°, so the hole is off-screen. The comment "looking at disk edge-on" (main.rs:56) is wrong. The camera also starts inside the disk's Gaussian envelope (density ≈ 0.018).
3. **The disk is nearly invisible.** Emission per step is about 0.2 × 0.01 (compute.wgsl:158, 256) times about 0.03 opacity, so the accumulated value is ≲ 0.01 linear, which ACES and sRGB turn into roughly 12/255. This is the result of the 04:00 "VERY conservative" anti-blowout clamps (:155, :255, :259, :269; NaN-magenta check at display.wgsl:63-69).
4. **No orange ever appears.** Temperatures are blended between 10⁴ K and 10⁷ K (main.rs:251-252) and normalised by 10⁴ (compute.wgsl:140), so every sample takes the "white→blue" branch. The disk is uniformly pale blue-white. Separately, the blend is a lerp with `pow(frac, 0.75)` (:124-128), not the power-law `T ∝ r^-0.75` its comment claims.
5. **Doppler beaming is inverted.** The code uses the ray direction (camera to scene) rather than the photon direction (scene to camera) (compute.wgsl:179, 248), so the receding side is brightened. It is also first-order and clamped.
6. **The image is likely upside-down (mirror-flipped).** Texture row 0 is the screen top (display.wgsl:12-22), but in compute row 0 gives `ndc.y = −1`, which points the ray along −up (compute.wgsl:295-305).
7. **The "geodesic" is not the null-geodesic equation.**
   - The code uses magnitude `1.5·Rs/r²` for every ray, adds a nonphysical `v_perp/r` term, and renormalises speed every step (compute.wgsl:77-91).
   - The correct Cartesian form is `a = −(3/2)·Rs·h²·r⃗/r⁵` with `h = |r⃗×v⃗|`, as used in Starless ([rantonels.github.io/starless](https://rantonels.github.io/starless/)).
   - `geodesic_acceleration` assumes the hole is at the origin (`length(pos)`, :65), while `trace_ray` uses `black_hole.position`.
   - `black_hole.mass` and `G` are never used.
8. **The starfield looks pixelated, which the owner explicitly does not want.**
   - Stars are single texels in a 2048×2048 square texture mapped equirectangularly (main.rs:525). The map should be 2:1, so stars are stretched 2× vertically and crowd toward the poles.
   - There are no mipmaps (:566), so each texel is magnified about 3.7× on screen.
   - The RNG returns values in [0, 2) (:541), so about 75% of the 50k stars fall off-texture; roughly 12.5k remain.
   - Every star is white: no colours and no Milky Way band.
9. **Precision rules out real scales.** Positions are f32 in hard-coded kilometres, with no floating origin or f64.
